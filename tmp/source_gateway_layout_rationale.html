Source Gateway Layout Rationale

为什么第一步要这样设文件夹？

因为第一阶段的目标不是“爬很多网页”，而是建立一条稳定的数据入口： 数据源可登记、adapter 可替换、输出可追溯、失败可复盘，后续数据挖掘、知识图谱和 Agent 都能复用。

configs 把源和 watchlist 写成配置，避免硬编码。
packages/core 定义系统自己的标准数据语言。
packages/ingestion 把外部源翻译成统一 schema。
data / tests 落样本、留 manifest，并用测试守住接口。

这不是过度设计

这棵树只分了最必要的边界：配置、核心 schema、接入逻辑、命令入口、输出数据和测试。 没有数据库、没有服务、没有队列、没有 Agent 框架。

它的价值是让第一批 6 个源都按同一种规则进来： SEC 和 IR 变成 Document，YFinance 变成 MarketContext， Tavily/Brave 变成 SearchLead，Stock Sentiment 变成 AttentionSignal。

一句话：先把入口做干净，后面再加数据挖掘、事件聚类、证据链和 Agent。
Reason 1

Source Registry 独立出来

数据源不是普通 URL 列表。它还要记录 source tier、source family、allowed use、rate limit、 API key 环境变量、版权和证据权限。

Reason 2

core 和 ingestion 分开

core 是我们的领域语言，应该稳定；ingestion 是外部适配层， 可以频繁改。这样换 Tavily、Brave 或行情源时，不会影响后面的证据链。

Reason 3

adapter skeleton 先统一接口

先让 6 个 adapter 都实现同一套输入输出，哪怕内部只是 skeleton。 这样主流程只关心 fetch、normalize、write。

Reason 4

JSONL 先替代数据库

JSONL 对 MVP 最友好：一行一条记录，可读、可 diff、可重跑、可导入 Postgres。 第一阶段不需要为了存储提前引入复杂基础设施。

Reason 5

manifest 是审计线索

每次运行都要知道哪些源成功、哪些失败、抓了多少条、错误是什么、raw 文件在哪里。 这比“命令跑完没报错”可靠得多。

Reason 6

tests 守住 schema 合约

早期测试不追求覆盖所有网络行为，先确认 registry 能读、schema 能校验、 adapter 输出类型一致、manifest 记录完整。

第一步运行时应该发生什么

1. 读配置 sources.yaml 和 watchlist.yaml 决定跑哪些源和 ticker。
2. 调 adapter SEC、IR、YFinance、Tavily、Brave、Sentiment 分别抓取小样本。
3. 保存 raw 原始响应放进 data/raw，保留 URL、时间、hash 和错误。
4. 标准化 输出 Document、MarketContext、SearchLead、AttentionSignal。
5. 写 manifest 在 data/runs 记录本次运行状态，方便复盘和重跑。

该做什么，不该做什么

第一阶段要做

  • 固定 3-5 个 ticker 跑通样本。
  • 每条数据都带 source_id、retrieved_at、content_hash。
  • 搜索 API 只输出 SearchLead，不直接当证据。
  • 失败写进 manifest，不让一个源拖死整次运行。

第一阶段先不做

  • 不做全网爬虫。
  • 不接数据库、队列、Dagster、LangGraph。
  • 不让 Agent 自由上网搜索。
  • 不把社交舆情当事实证据。
最小成功标准：一个命令能产出 raw 文件、normalized JSONL 和 manifest，并且 6 个源的输出类型边界清楚。
